# 系统性调试

## 概述

随机修复会浪费时间并引入新漏洞。快速补丁会掩盖深层问题。

**核心原则：** 在尝试任何修复之前，务必找到根本原因。修复症状即是失败。

**违反此流程的字面规定，即违反调试精神。**

## 铁律

```
未经根本原因调查，不得进行任何修复
```

如果你尚未完成第一阶段，则不能提出修复方案。

## 适用场景

适用于任何技术问题：
- 测试失败
- 生产环境漏洞
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**尤其在以下情况时使用：**
- 时间紧迫（紧急情况容易引发猜测）
- "只需快速修复一下"看似显而易见
- 已尝试过多种修复方案
- 上一次修复未能奏效
- 对问题尚未完全理解

**以下情况不得跳过：**
- 问题看似简单（简单的漏洞也有根本原因）
- 时间紧迫（急于求成必然导致返工）
- 管理者要求立即修复（系统性方法比反复试错更快）

## 四个阶段

在进入下一阶段之前，必须完成当前阶段。

### 第一阶段：根本原因调查

**在尝试任何修复之前：**

1. **仔细阅读错误信息**
   - 不要跳过错误或警告
   - 错误信息通常包含确切的解决方案
   - 完整阅读堆栈跟踪
   - 记录行号、文件路径、错误代码

2. **稳定复现**
   - 能否可靠地触发该问题？
   - 具体步骤是什么？
   - 是否每次都会出现？
   - 如果无法复现 → 收集更多数据，不要猜测

3. **检查近期变更**
   - 哪些变更可能导致了这个问题？
   - Git diff、近期提交记录
   - 新增依赖、配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统包含多个组件时（CI → 构建 → 签名，API → 服务 → 数据库）：**

   **在提出修复方案之前，添加诊断探针：**
   ```
   对每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置的传递
     - 检查每层的状态

   运行一次以收集证据，找出故障发生在哪里
   然后分析证据，确定故障组件
   再对该具体组件展开调查
   ```

   **示例（多层系统）：**
   ```bash
   # 第一层：工作流
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # 第二层：构建脚本
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # 第三层：签名脚本
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # 第四层：实际签名
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **此方法可揭示：** 哪一层出现故障（密钥 → 工作流 ✓，工作流 → 构建 ✗）

5. **追踪数据流**

   **当错误深藏于调用堆栈时：**

   请参阅本目录中的 `root-cause-tracing.md`，了解完整的反向追踪技术。

   **简要说明：**
   - 错误值从哪里产生？
   - 是谁以错误值调用了此处？
   - 持续向上追踪，直到找到来源
   - 在来源处修复，而非在症状处修复

### 第二阶段：模式分析

**在修复之前找到规律：**

1. **查找可工作的示例**
   - 在同一代码库中找到类似的可工作代码
   - 与出问题的代码相似的、能正常运行的是什么？

2. **对比参考实现**
   - 如果正在实现某种模式，请完整阅读参考实现
   - 不要略读——逐行阅读
   - 在应用之前完全理解该模式

3. **识别差异**
   - 可工作与出问题的代码之间有什么不同？
   - 列出每一处差异，无论多小
   - 不要假设"这不可能有影响"

4. **理解依赖关系**
   - 这个组件还需要哪些其他组件？
   - 需要哪些设置、配置、环境？
   - 它做了哪些假设？

### 第三阶段：假设与验证

**科学方法：**

1. **形成单一假设**
   - 清晰陈述："我认为 X 是根本原因，因为 Y"
   - 写下来
   - 要具体，不要含糊

2. **最小化测试**
   - 做出可能最小的改动来验证假设
   - 每次只改变一个变量
   - 不要同时修复多个问题

3. **在继续之前验证**
   - 成功了吗？是 → 进入第四阶段
   - 没有成功？形成新的假设
   - 不要在此基础上叠加更多修复

4. **当你不确定时**
   - 说"我不理解 X"
   - 不要假装知道
   - 寻求帮助
   - 深入研究

### 第四阶段：实施

**修复根本原因，而非症状：**

1. **创建失败的测试用例**
   - 尽可能简单的复现
   - 如果可能，使用自动化测试
   - 如果没有测试框架，使用一次性测试脚本
   - 修复之前必须先有测试
   - 使用 `superpowers:test-driven-development` 技能编写正确的失败测试

2. **实施单一修复**
   - 针对已识别的根本原因
   - 每次只做一处变更
   - 不要"顺便"做改进
   - 不要捆绑重构

3. **验证修复**
   - 测试现在通过了吗？
   - 没有破坏其他测试吗？
   - 问题真正解决了吗？

4. **如果修复无效**
   - 停止
   - 统计：你已经尝试了几次修复？
   - 如果少于 3 次：返回第一阶段，结合新信息重新分析
   - **如果达到或超过 3 次：停止并质疑架构（见下面的第 5 步）**
   - 未经架构讨论，不得尝试第 4 次修复

5. **如果 3 次以上修复均告失败：质疑架构**

   **表明架构问题的迹象：**
   - 每次修复都在不同地方暴露出新的共享状态/耦合/问题
   - 修复需要"大规模重构"才能实施
   - 每次修复都在其他地方产生新症状

   **停止并质疑根本原理：**
   - 这个模式从根本上是合理的吗？
   - 我们是否在"凭惯性坚持下去"？
   - 我们应该重构架构，还是继续修复症状？

   **在尝试更多修复之前，与你的合作伙伴讨论**

   这不是假设失败——这是架构错误。

## 红色警报——停止并遵循流程

如果你发现自己在想：
- "先快速修复，之后再调查"
- "就试试改 X，看看是否有效"
- "做多处改动，运行测试"
- "跳过测试，手动验证"
- "可能是 X，让我修一下"
- "我还不完全理解，但这也许能行"
- "模式说的是 X，但我会用不同方式来适配"
- "这是主要问题：[在没有调查的情况下列出修复方案]"
- 在追踪数据流之前提出解决方案
- **"再试一次修复"（已经试了 2 次以上时）**
- **每次修复都在不同地方暴露出新问题**

**以上所有情况意味着：停止。返回第一阶段。**

**如果 3 次以上修复均告失败：** 质疑架构（见第四阶段第 5 步）

## 合作伙伴发出的信号表明你走偏了

**留意这些重新引导：**
- "那种情况没有出现吗？"——你在未经验证的情况下做了假设
- "这能告诉我们……吗？"——你应该添加证据收集
- "别猜了"——你在没有理解的情况下提出修复方案
- "深入思考一下"——质疑根本原理，而不只是症状
- "我们卡住了？"（沮丧）——你的方法行不通

**当你看到这些信号时：** 停止。返回第一阶段。

## 常见合理化借口

| 借口 | 现实 |
|------|------|
| "问题很简单，不需要流程" | 简单问题也有根本原因。对于简单漏洞，流程反而更快。 |
| "紧急情况，没时间走流程" | 系统性调试比猜测式反复试错更快。 |
| "先试试这个，然后再调查" | 第一次修复奠定了行为模式。一开始就做正确的事。 |
| "确认修复有效后再写测试" | 未经测试的修复无法持久。先测试才能证明它有效。 |
| "同时多处修复能节省时间" | 无法确定是哪个修复起了作用。还会引入新漏洞。 |
| "参考太长了，我来适配这个模式" | 理解不完整必然导致漏洞。完整阅读它。 |
| "我看到问题了，让我来修" | 看到症状 ≠ 理解根本原因。 |
| "再试一次修复"（2 次以上失败后） | 3 次以上失败 = 架构问题。质疑模式，不要再修了。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|------|---------|---------|
| **1. 根本原因** | 阅读错误、复现、检查变更、收集证据 | 理解是什么以及为什么 |
| **2. 模式** | 查找可工作示例、对比 | 识别差异 |
| **3. 假设** | 形成理论、最小化测试 | 确认或形成新假设 |
| **4. 实施** | 创建测试、修复、验证 | 漏洞解决，测试通过 |

## 当流程揭示"没有根本原因"时

如果系统性调查揭示问题确实是环境性、时序相关或外部因素导致的：

1. 你已完成了这个流程
2. 记录你所调查的内容
3. 实施适当的处理（重试、超时、错误信息）
4. 添加监控/日志以供未来调查

**但是：** 95% 的"没有根本原因"情况都是调查不完整。

## 辅助技术

这些技术是系统性调试的组成部分，可在本目录中找到：

- **`root-cause-tracing.md`** — 通过调用堆栈反向追踪漏洞，找到最初触发点
- **`defense-in-depth.md`** — 找到根本原因后在多个层级添加验证
- **`condition-based-waiting.md`** — 用条件轮询替换任意超时

**相关技能：**
- **superpowers:test-driven-development** — 用于创建失败测试用例（第四阶段第 1 步）
- **superpowers:verification-before-completion** — 在宣告成功之前验证修复有效

## 实际效果

来自调试会话的数据：
- 系统性方法：15-30 分钟解决
- 随机修复方法：2-3 小时反复试错
- 一次性修复成功率：95% 对比 40%
- 引入新漏洞数量：几乎为零 对比 较为常见
