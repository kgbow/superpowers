# 基于用户反馈的技能改进

**日期：** 2025-11-28
**状态：** 草稿
**来源：** 两个在真实开发场景中使用 superpowers 的 Claude 实例

---

## 执行摘要

两个 Claude 实例提供了来自实际开发会话的详细反馈。其反馈揭示了当前技能中**系统性的缺陷**，这些缺陷使得可预防的漏洞即使在遵循技能规范的情况下仍然发布出去。

**关键洞察：** 这些是问题报告，而非单纯的解决方案提案。问题是真实存在的；解决方案需要仔细评估。

**核心主题：**
1. **验证缺口** - 我们验证操作是否成功，但不验证其是否达到预期结果
2. **流程卫生** - 后台进程在各子代理间累积并相互干扰
3. **上下文优化** - 子代理获得了过多无关信息
4. **缺乏自我反思** - 在交接前没有提示批判自身工作
5. **Mock 安全性** - Mock 可能在不被察觉的情况下与接口产生偏差
6. **技能激活** - 技能存在但未被读取/使用

---

## 已识别的问题

### 问题 1：配置变更验证缺口

**发生了什么：**
- 子代理测试"OpenAI 集成"
- 设置了 `OPENAI_API_KEY` 环境变量
- 得到了 200 状态码响应
- 报告"OpenAI 集成正常工作"
- **但是**响应包含 `"model": "claude-sonnet-4-20250514"` — 实际上在使用 Anthropic

**根本原因：**
`verification-before-completion` 检查操作是否成功，但不检查结果是否反映了预期的配置变更。

**影响：** 高 - 对集成测试产生虚假信心，导致漏洞发布到生产环境

**示例失败模式：**
- 切换 LLM 提供商 → 验证状态 200，但不检查模型名称
- 启用功能标志 → 验证无错误，但不检查功能是否已激活
- 更改环境 → 验证部署成功，但不检查环境变量

---

### 问题 2：后台进程累积

**发生了什么：**
- 会话期间分派了多个子代理
- 每个子代理启动了后台服务器进程
- 进程累积（4+ 个服务器在运行）
- 旧进程仍然绑定到端口
- 后续的端到端测试命中了配置错误的旧服务器
- 产生混乱/错误的测试结果

**根本原因：**
子代理是无状态的——不知道前一个子代理的进程。没有清理协议。

**影响：** 中高 - 测试命中错误的服务器，产生虚假的通过/失败，调试困难

---

### 问题 3：子代理提示中的上下文膨胀

**发生了什么：**
- 标准方法：让子代理读取完整的计划文件
- 实验：只提供任务 + 模式 + 文件 + 验证命令
- 结果：更快、更专注，一次完成的情况更常见

**根本原因：**
子代理在无关的计划部分上浪费令牌和注意力。

**影响：** 中 - 执行速度变慢，失败尝试增多

**有效的方法：**
```
You are adding a single E2E test to packnplay's test suite.

**Your task:** Add `TestE2E_FeaturePrivilegedMode` to `pkg/runner/e2e_test.go`

**What to test:** A local devcontainer feature that requests `"privileged": true`
in its metadata should result in the container running with `--privileged` flag.

**Follow the exact pattern of TestE2E_FeatureOptionValidation** (at the end of the file)

**After writing, run:** `go test -v ./pkg/runner -run TestE2E_FeaturePrivilegedMode -timeout 5m`
```

### 问题 4：交接前缺乏自我反思

**发生了什么：**
- 添加了自我反思提示："用新鲜的眼光看你的工作——有什么可以改进的？"
- 任务 5 的实现者识别出失败的测试是由于实现漏洞，而非测试漏洞
- 追踪到第 99 行：`strings.Join(metadata.Entrypoint, " ")` 创建了无效的 Docker 语法
- 没有自我反思，实现者会只报告"测试失败"而不给出根本原因

**根本原因：**
实现者不会自然地在汇报完成之前退后一步，批判自己的工作。

**影响：** 中 - 实现者本可发现的漏洞被交接给了审查者

---

### 问题 5：Mock 与接口的偏差

**发生了什么：**
```typescript
// 接口定义了 close()
interface PlatformAdapter {
  close(): Promise<void>;
}

// 代码（有漏洞）调用 cleanup()
await adapter.cleanup();

// Mock（与漏洞匹配）定义了 cleanup()
vi.mock('web-adapter', () => ({
  WebAdapter: vi.fn().mockImplementation(() => ({
    cleanup: vi.fn().mockResolvedValue(undefined),  // 错误！
  })),
}));
```
- 测试通过
- 运行时崩溃："adapter.cleanup is not a function"

**根本原因：**
Mock 从有漏洞的代码调用推导，而非从接口定义推导。TypeScript 无法捕获方法名错误的内联 Mock。

**影响：** 高 - 测试给出虚假信心，运行时崩溃

**为什么 testing-anti-patterns 未能预防这个问题：**
该技能涵盖了测试 Mock 行为和在不理解的情况下 Mock，但未涵盖"从接口而非实现推导 Mock"这一特定模式。

---

### 问题 6：代码审查者文件访问

**发生了什么：**
- 分派了代码审查者子代理
- 找不到测试文件："The file doesn't appear to exist in the repository"
- 文件实际上存在
- 审查者不知道需要先明确读取它

**根本原因：**
审查者提示中不包含明确的文件读取指令。

**影响：** 低中 - 审查失败或不完整

---

### 问题 7：修复工作流延迟

**发生了什么：**
- 实现者在自我反思期间识别出漏洞
- 实现者知道如何修复
- 当前工作流：报告 → 我分派修复者 → 修复者修复 → 我验证
- 额外的往返增加了延迟，但没有增加价值

**根本原因：**
当实现者已经诊断出问题时，实现者和修复者角色之间的严格分离是多余的。

**影响：** 低 - 有延迟，但不影响正确性

---

### 问题 8：技能未被读取

**发生了什么：**
- `testing-anti-patterns` 技能存在
- 人类和子代理在编写测试前都没有读取它
- 可能预防了一些问题（尽管不是全部——参见问题 5）

**根本原因：**
没有强制子代理读取相关技能的机制。没有任何提示包含技能读取要求。

**影响：** 中 - 如果技能不被使用，技能投入就白费了

## 改进提案

### 1. verification-before-completion：添加配置变更验证

**新增章节：**

```markdown
## 验证配置变更

在测试配置、提供商、功能标志或环境的变更时：

**不要只验证操作是否成功。要验证输出是否反映了预期的变更。**

### 常见失败模式

操作成功是因为*存在某个*有效配置，但不是您打算测试的配置。

### 示例

| 变更 | 不充分的验证 | 必要的验证 |
|------|-------------|-----------|
| 切换 LLM 提供商 | 状态 200 | 响应包含预期的模型名称 |
| 启用功能标志 | 无错误 | 功能行为实际已激活 |
| 更改环境 | 部署成功 | 日志/变量引用新环境 |
| 设置凭证 | 认证成功 | 已认证的用户/上下文是正确的 |

### 门控函数

```
在声称配置变更有效之前：

1. 识别：此变更后什么应该不同？
2. 定位：在哪里可以观察到这种差异？
   - 响应字段（模型名称、用户 ID）
   - 日志行（环境、提供商）
   - 行为（功能激活/停用）
3. 运行：显示可观察差异的命令
4. 验证：输出包含预期的差异
5. 仅此之后：声称配置变更有效

警示信号：
  - "请求成功"但不检查内容
  - 检查状态码但不检查响应体
  - 验证无错误但无正面确认
```

**为什么有效：**
强制验证意图，而非仅验证操作成功。

### 2. subagent-driven-development：为端到端测试添加流程卫生

**新增章节：**

```markdown
## 端到端测试的流程卫生

当分派启动服务（服务器、数据库、消息队列）的子代理时：

### 问题

子代理是无状态的——它们不知道前一个子代理启动的进程。后台进程会持续存在并干扰后续测试。

### 解决方案

**在分派端到端测试子代理之前，在提示中包含清理指令：**

```
在启动任何服务之前：
1. 终止现有进程：pkill -f "<service-pattern>" 2>/dev/null || true
2. 等待清理：sleep 1
3. 验证端口空闲：lsof -i :<port> && echo "ERROR: Port still in use" || echo "Port free"

测试完成后：
1. 终止您启动的进程
2. 验证清理：pgrep -f "<service-pattern>" || echo "Cleanup successful"
```

### 示例

```
任务：运行 API 服务器的端到端测试

提示包含：
"在启动服务器之前：
- 终止任何现有服务器：pkill -f 'node.*server.js' 2>/dev/null || true
- 验证端口 3001 空闲：lsof -i :3001 && exit 1 || echo 'Port available'

测试后：
- 终止您启动的服务器
- 验证：pgrep -f 'node.*server.js' || echo 'Cleanup verified'"
```

### 为什么重要

- 旧进程用错误配置响应请求
- 端口冲突导致静默失败
- 进程累积拖慢系统
- 混乱的测试结果（命中错误服务器）
```

**权衡分析：**
- 向提示添加了样板代码
- 但防止了非常令人困惑的调试
- 对于端到端测试子代理值得这样做

### 3. subagent-driven-development：添加精简上下文选项

**修改步骤 2：用子代理执行任务**

**之前：**
```
从 [plan-file] 仔细读取该任务。
```

**之后：**
```
## 上下文方法

**完整计划（默认）：**
当任务复杂或有依赖关系时使用：
```
仔细从 [plan-file] 读取任务 N。
```

**精简上下文（适用于独立任务）：**
当任务是独立的且基于模式时使用：
```
您正在实现：[1-2 句任务描述]

要修改的文件：[确切路径]
要遵循的模式：[对现有函数/测试的引用]
要实现的内容：[具体要求]
验证命令：[确切命令]

[不要包含完整的计划文件]
```

**在以下情况使用精简上下文：**
- 任务遵循现有模式（添加类似测试、实现类似功能）
- 任务是自包含的（不需要其他任务的上下文）
- 模式引用已足够（例如："遵循 TestE2E_FeatureOptionValidation"）

**在以下情况使用完整计划：**
- 任务依赖其他任务
- 需要理解整体架构
- 需要上下文的复杂逻辑
```

**示例：**
```
精简上下文提示：

"您正在为 devcontainer 功能的特权模式添加测试。

文件：pkg/runner/e2e_test.go
模式：遵循 TestE2E_FeatureOptionValidation（位于文件末尾）
测试：元数据中包含 `"privileged": true` 的功能应导致容器以 `--privileged` 标志运行
验证：go test -v ./pkg/runner -run TestE2E_FeaturePrivilegedMode -timeout 5m

报告：实现情况、测试结果、任何问题。"
```

**为什么有效：**
减少令牌使用，增加专注度，在适当情况下更快完成。

### 6. testing-anti-patterns：添加 Mock 与接口偏差反模式

**添加新的反模式 6：**

```markdown
## 反模式 6：从实现推导 Mock

**违规情况：**
```typescript
// 代码（有漏洞）调用 cleanup()
await adapter.cleanup();

// Mock（与漏洞匹配）有 cleanup()
const mock = {
  cleanup: vi.fn().mockResolvedValue(undefined)
};

// 接口（正确）定义了 close()
interface PlatformAdapter {
  close(): Promise<void>;
}
```

**为什么这是错误的：**
- Mock 将漏洞编码进了测试
- TypeScript 无法捕获方法名错误的内联 Mock
- 测试通过是因为代码和 Mock 都是错的
- 使用真实对象时运行时崩溃

**修复方法：**
```typescript
// ✅ 正确：从接口推导 Mock

// 步骤 1：打开接口定义（PlatformAdapter）
// 步骤 2：列出那里定义的方法（close、initialize 等）
// 步骤 3：Mock 恰好那些方法

const mock = {
  initialize: vi.fn().mockResolvedValue(undefined),
  close: vi.fn().mockResolvedValue(undefined),  // 来自接口！
};

// 现在测试会失败，因为代码调用了 Mock 中不存在的 cleanup()
// 这个失败在运行时之前就揭示了漏洞
```

### 门控函数

```
在编写任何 Mock 之前：

  1. 停止 - 暂时不要看被测试的代码
  2. 查找：依赖项的接口/类型定义
  3. 读取：接口文件
  4. 列出：接口中定义的方法
  5. Mock：只有那些方法，且使用完全相同的名称
  6. 不要：查看您的代码调用了什么

  如果您的测试失败，因为代码调用了 Mock 中不存在的方法：
    ✅ 好现象 - 测试在您的代码中发现了漏洞
    修复代码以调用正确的接口方法
    而不是修改 Mock

  警示信号：
    - "我来 Mock 代码调用的内容"
    - 从实现复制方法名
    - 不读接口就写 Mock
    - "测试失败了，所以我要在 Mock 中添加这个方法"
```

**检测方法：**

当您看到运行时错误"X is not a function"但测试通过时：
1. 检查 X 是否被 Mock
2. 将 Mock 方法与接口方法进行比较
3. 查找方法名不匹配
```

**为什么有效：**
直接解决了反馈中的失败模式。

### 8. subagent-driven-development：允许实现者修复自己发现的问题

**修改步骤 2：**

**当前：**
```
子代理汇报工作摘要。
```

**提案：**
```
子代理执行自我反思，然后：

如果自我反思发现可修复的问题：
  1. 修复问题
  2. 重新运行验证
  3. 汇报："初始实现 + 自我反思修复"

否则：
  汇报："实现完成"

- 自我反思发现
- 是否应用了修复
- 最终验证结果
```

**为什么有效：**
当实现者已经知道修复方法时，减少延迟。记录在案的案例：可以为入口点漏洞节省一次往返。

**权衡：**
提示略微复杂，但端到端速度更快。

1. **精简上下文方法：**
   - 是否应该将其设为基于模式任务的默认方式？

## 风险与缓解措施

### 风险：提示膨胀
**问题：** 添加所有这些要求会使提示变得让人不知所措
**缓解措施：**
- 分阶段实施（不要一次添加所有内容）
- 使部分添加有条件（端到端卫生仅用于端到端测试）
- 考虑针对不同任务类型使用模板

### 风险：分析瘫痪
**问题：** 过多的反思/验证拖慢执行
**缓解措施：**
- 保持门控函数简短（秒级，而非分钟级）
- 最初将精简上下文设为可选
- 监控任务完成时间

### 风险：虚假安全感
**问题：** 遵循清单不能保证正确性
**缓解措施：**
- 强调门控函数是最低标准，而非最高标准
- 在技能中保留"运用判断"的表述
- 记录技能捕获常见失败，而非所有失败

### 风险：技能发散
**问题：** 不同技能给出相互矛盾的建议
**缓解措施：**
- 审查所有技能的变更以确保一致性
- 记录技能的交互方式（集成章节）
- 在部署前用真实场景进行测试
