# Superpowers 设计思路与哲学深度解析

## 前言

Superpowers 不是一个普通的提示词集合，也不是一堆"让 AI 表现更好"的技巧列表。它是一套**强制执行的工作流操作系统**，专门为解决一个根本问题而设计：AI 智能体在压力下会走捷径、合理化违规行为，并跳过那些"感觉多余"的步骤——而恰恰是这些步骤保证了质量。

理解 Superpowers 的设计，首先要理解它所对抗的敌人：**智能体的合理化能力**。

---

## 一、核心设计哲学

### 1.1 强制执行，而非建议

Superpowers 中几乎每一个核心技能都有一条"铁律"（Iron Law），格式固定：

```
NO [行动] WITHOUT [前置条件] FIRST
```

- `NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST`（TDD）
- `NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST`（系统性调试）
- `NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE`（完成前验证）
- `NO SKILL WITHOUT A FAILING TEST FIRST`（编写技能）

这种格式不是修辞技巧，而是经过测试后发现的最有效的约束方式。它的关键在于：**把规则从"应该做"变成"不做就是违规"**。

普通建议："你应该先写测试。"
铁律："没有失败的测试，就没有生产代码。"

第一种说法给智能体留下了判断空间，它可以说"这个场景太简单了，不需要"。第二种说法关闭了这个空间。

### 1.2 明确对抗合理化

每个强制性技能都包含一张"合理化表格"，列出智能体最常用的借口，并逐一反驳：

| 借口 | 现实 |
|------|------|
| "太简单了，不需要测试" | 简单的代码也会出错。测试只需 30 秒。|
| "我会在之后测试" | 之后写的测试立刻通过，什么都证明不了。|
| "手动测试过了" | 临时测试 ≠ 系统性测试，无法重复运行。|
| "删掉几小时的工作太浪费了" | 沉没成本谬误。无法信任的代码才是浪费。|

这些表格来源于实际测试：开发者让智能体在"压力场景"下运行（时间压力、沉没成本压力、权威压力），记录智能体实际使用的借口，然后把这些借口写进技能文档，逐条封堵。

### 1.3 流程先于直觉

整个系统的主轴是：**在做任何事之前，先检查是否有适用的技能**。

`using-superpowers` 技能（在每个会话开始时自动注入）的核心规则：

> 哪怕只有 1% 的可能性某个技能适用，你也必须调用它。

这个规则看起来激进，但它解决了一个真实问题：智能体在面对"感觉简单"的任务时，会跳过流程，直接行动。而"感觉简单"正是最危险的时刻——因为未经审视的假设在简单项目中造成的浪费最多。

### 1.4 证据先于声明

`verification-before-completion` 技能规定：在声明任何工作完成之前，必须运行验证命令并展示输出。

```
✅ [运行测试] [看到：34/34 通过] → "所有测试通过"
❌ "应该没问题了" / "看起来正确"
```

这个原则来自一个观察：AI 智能体非常擅长生成令人信服的"成功感"，即使实际上什么都没有验证。系统通过要求具体证据来打破这种模式。

## 二、层层嵌套的工作流架构

Superpowers 的工作流是一个五层嵌套结构，每一层都为下一层提供约束和上下文。

```
第 0 层：基础设施（SessionStart Hook）
    └── 第 1 层：元控制器（using-superpowers）
            └── 第 2 层：主工作流（brainstorming → writing-plans → 执行）
                    └── 第 3 层：技能内部流程（每个技能的子工作流）
                            └── 第 4 层：子智能体（实现 / 审查循环）
```

### 第 0 层：基础设施 — SessionStart Hook

每次会话启动时，`hooks/session-start` 脚本自动执行，将 `using-superpowers` 技能的完整内容注入到智能体的上下文中。

这一层解决的问题是**冷启动**：如果智能体需要主动去查找"如何使用技能"的说明，它可能不会去查。通过 Hook 强制注入，确保智能体在回复第一条消息之前已经知道规则。

`hooks/run-hook.cmd` 是一个多平台兼容的包装器（Windows 批处理 + Unix bash 的双语脚本），确保 Hook 在所有操作系统上都能正常运行。

### 第 1 层：元控制器 — using-superpowers

这是整个系统的"宪法"层。它规定了一条超越所有其他规则的元规则：

```
在做任何事之前，检查是否有适用的技能。技能说 WHAT，不说 HOW。
"添加 X"或"修复 Y"不等于跳过工作流。
```

这一层还定义了技能优先级：
1. **流程技能优先**（brainstorming、debugging）——决定如何处理任务
2. **实现技能其次**（特定技术技能）——指导具体执行

当用户说"让我们构建 X"时，这一层拦截请求，先触发 `brainstorming`，再进行具体实现。

### 第 2 层：主工作流 — 标准开发流水线

```
brainstorming
    → writing-plans
        → [选择执行模式]
            ├── subagent-driven-development（同会话，快速迭代）
            └── executing-plans（并行会话，批量执行）
```

**brainstorming（头脑风暴）**

在写任何代码之前强制进行的设计阶段。包含一个硬性门控：

```
<HARD-GATE>
在向用户展示设计并获得批准之前，不得调用任何实现技能、
编写任何代码、搭建任何项目框架，或采取任何实现行动。
无论项目有多简单，此规则适用于所有项目。
</HARD-GATE>
```

六步强制清单：
1. 探索项目上下文
2. 一次只问一个澄清问题
3. 提出 2-3 种方案并比较权衡
4. 分段呈现设计，逐段获得批准
5. 将设计文档写入 `docs/plans/YYYY-MM-DD-<主题>-design.md`
6. 过渡到 `writing-plans` 技能

设计文档存入 git，提供可追溯的决策记录。

**writing-plans（编写计划）**

将已批准的设计转化为极度细粒度的实现计划。每个任务大约 2-5 分钟，包含：
- 精确的文件路径
- 完整的代码（不是"添加验证"这种模糊指令）
- 精确的命令和预期输出
- TDD 步骤（写失败测试→确认失败→写最小实现→确认通过→提交）

计划文件的首部必须包含一个内嵌指令，告诉执行它的智能体要使用哪个技能来执行：

```markdown
> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.
```

这个设计很精妙：计划文件本身携带执行指令，即使在全新的会话中打开，智能体也能知道正确的执行方式。

**执行阶段的两条路径**

计划完成后，有两种执行模式：

| 特性 | subagent-driven-development | executing-plans |
|------|------|------|
| 会话 | 同一个会话 | 新的并行会话 |
| 人工干预 | 任务间自动继续 | 批次间有检查点 |
| 速度 | 更快 | 适合长期项目 |
| 上下文 | 主智能体维护状态 | 每个批次独立 |

### 第 3 层：技能内部流程

每个技能不仅是一组指令，而是一个完整的子工作流，包含自己的决策图（Graphviz dot 格式）、检查表和失败处理逻辑。

以 `subagent-driven-development` 为例，其内部流程：

```
读取计划（一次性，不重复读）
    → 提取所有任务的完整文本
    → 创建 TodoWrite 任务列表
    → 对每个任务循环：
        → 派发实现子智能体
            → [子智能体先问问题，再实现，再自我审查，再提交]
        → 派发规格合规审查子智能体
            → [不合规 → 实现子智能体修复 → 重新审查]
        → 派发代码质量审查子智能体
            → [不合规 → 实现子智能体修复 → 重新审查]
        → 标记任务完成
    → 派发最终代码审查子智能体
    → 调用 finishing-a-development-branch 技能
```

审查顺序（规格合规在前，代码质量在后）是刻意设计的：先确认"构建了正确的东西"，再确认"构建方式是否正确"。颠倒顺序会导致对不符合规格的代码进行质量优化，浪费时间。

### 第 4 层：子智能体 — 独立的执行单元

子智能体是整个系统中最底层的执行单元，设计原则是**上下文隔离**：

**为什么每个任务都需要一个新的子智能体？**

在同一个智能体内连续执行多个任务，会导致"上下文污染"：早期任务的错误假设会影响后续任务的判断，错误决策的"惯性"会累积。每次使用全新的子智能体，就像每个任务都有一个头脑清醒、没有包袱的工程师来执行。

**子智能体不读取文件，主智能体提供完整文本**

子智能体在提示词中已经获得完整的任务描述，不需要自己去读计划文件。这消除了文件读取开销，也消除了子智能体因为"读到了额外内容"而偏离任务的风险。

**两阶段审查的独立性**

规格审查员"不相信实现者的报告"，而是独立读取代码来验证。这模拟了真实工程团队中的独立审查：你不能因为实现者说"已完成"就认为工作完成了。

## 三、技能发现机制的设计

理解 Superpowers 的架构，还需要理解技能是如何被"找到"的。

### description 字段的反直觉设计

技能的 `description` 字段有一条反直觉的规则：**只描述触发条件，绝不描述工作流程**。

```yaml
# ❌ 错误：总结了工作流
description: Use when executing plans - dispatches subagent per task with code review between tasks

# ✅ 正确：只描述触发条件
description: Use when executing implementation plans with independent tasks in the current session
```

为什么？因为经过测试发现：当 description 总结了工作流，智能体会把 description 当作"完整指令"来执行，跳过读取技能全文。结果是智能体执行了描述中提到的一次审查，而不是技能正文中规定的两次审查（规格合规 + 代码质量）。

这是一个精妙的认知陷阱：越"方便"的描述，越容易成为智能体偷懒的借口。

### 技能搜索的路径

`lib/skills-core.js` 实现了技能解析逻辑：

1. 解析每个 `SKILL.md` 的 YAML frontmatter，提取 `name` 和 `description`
2. 智能体看到描述后，决定是否调用该技能
3. 个人技能（`~/.claude/skills/`）优先于 Superpowers 内置技能（同名覆盖）
4. 技能可用 `superpowers:技能名` 前缀强制引用内置版本

## 四、测试驱动的技能开发

Superpowers 本身的技能也遵循 TDD 原则，但这里的"测试"是对智能体行为的测试。

### 技能开发的 RED-GREEN-REFACTOR

**RED（红）**：在没有技能的情况下，运行"压力场景"（多种压力同时施加：时间压力、沉没成本压力、权威压力），记录智能体实际的违规行为和使用的借口。

**GREEN（绿）**：根据记录的借口编写技能，让智能体在同样的压力下合规。

**REFACTOR（重构）**：识别新的合理化路径，明确堵塞，直到技能"防弹"。

这个过程解释了为什么 Superpowers 的技能文档那么详细，那么多"不得"和"不允许"：每一条禁止规则背后，都有一个智能体在测试中实际使用的借口。

### 测试的验证方法

集成测试通过以下方式验证技能效果：

1. 以无界面模式（headless mode）运行真实的 Claude Code 会话
2. 解析 `.jsonl` 格式的会话记录文件
3. 验证技能工具是否被调用、子智能体是否被派发、TodoWrite 是否被使用、文件是否被创建、测试是否通过
4. 分析 token 使用量，确保技能不会过度消耗上下文

## 五、对个人工作流设计的指导

理解了 Superpowers 的设计哲学，我们可以提炼出一套通用的个人工作流设计原则。

### 5.1 区分"建议"和"强制"

设计个人工作流时，首先要诚实地问：这条规则是"希望自己遵守"还是"必须遵守"？

对于真正重要的规则（比如"不在主分支直接提交"、"修改前必须读懂代码"），使用强制性语言和铁律格式。对于偏好性规则（比如"尽量用函数式风格"），用建议性语言即可。

混淆两者会导致所有规则都变成"可以商量"的建议，最终都不被遵守。

### 5.2 明确封堵合理化路径

写下一条规则后，问自己：**在什么压力下，我最可能找借口不遵守？**

把这些借口写下来，逐一反驳，并把这些反驳写进规则文档。不是因为你不信任自己，而是因为在压力下的自己会优先寻找捷径——每个人都是如此。

### 5.3 工作流要有"门控"

每个重要转换点（从设计到实现、从实现到声明完成）都应该有一个门控条件，不满足条件就不能通过。

门控的价值在于：它把决策从"每次都要判断"变成了"规则已经决定了"，减少了在疲惫或压力下做出糟糕判断的机会。

### 5.4 设计知识传递机制

Superpowers 解决了一个关键问题：如何让每一个新的智能体（或新会话）都能快速理解上下文和规则？

答案是多层传递：
- 技能文件（永久知识）
- 计划文件（项目级知识，并在文件头部内嵌执行指令）
- 设计文档（决策历史）
- 任务列表 TodoWrite（当前会话状态）

在个人工作流中，对应的设计是：
- `CLAUDE.md` / 项目文档：永久规则和架构决策
- 实现计划：当前任务的详细步骤
- 设计文档：为什么做出这个决策（而不仅仅是做了什么）
- Commit message：每个提交的意图

### 5.5 测试你的工作流，而不是假设它有效

Superpowers 中技能的开发过程就是一个示范：在你写下规则之前，先看看没有规则时会发生什么。

对于个人工作流，这意味着：
- 新流程试行一段时间后，检查有多少次被遵守，有多少次被跳过
- 记录每次跳过的借口
- 根据实际情况而不是理想状态来修订流程

### 5.6 上下文隔离原则

Superpowers 使用 git worktree 做代码隔离，用新的子智能体做上下文隔离。这个原则可以推广：

**不同类型的工作需要不同的"上下文容器"**：
- 长期项目与短期实验应该物理隔离（不同分支、不同目录）
- 调试工作与功能开发不应该混用同一个"脑力资源"
- 审查工作（检查别人的代码）不应该在实现工作（写代码）的同一心理状态下进行

### 5.7 粒度设计：2-5 分钟原则

`writing-plans` 要求每个任务步骤只需 2-5 分钟。这个粒度设计有几个关键作用：

1. **可验证性**：小步骤有清晰的完成标准
2. **可恢复性**：失败时损失最小
3. **可并行化**：独立的小任务可以分配给不同的执行单元
4. **防止过度工程**：步骤越小，越难在里面塞进 YAGNI 的功能

在设计个人任务时，如果一个步骤"感觉太大"，它可能确实太大了。把它拆分，直到你能用一句话精确描述"完成了什么，如何验证"。

### 5.8 "铁律"应该包含的四个要素

根据 Superpowers 的经验，一条有效的强制性规则应该包含：

1. **正向声明**：规则是什么（`NO X WITHOUT Y FIRST`）
2. **违规后果**：违规时要做什么（删除代码，重新开始）
3. **无例外列表**：明确列出常见的例外请求（"不保留作参考"、"不'边写测试边调整'"）
4. **合理化表格**：列出最常见的借口并逐一反驳

缺少任何一个要素都会削弱规则的约束力。

## 六、设计哲学总结

Superpowers 的本质是：**把软件工程的最佳实践从"我知道应该这样做"变成"我没有其他选择"**。

它所对抗的核心问题不是能力问题，而是**在压力下的纪律问题**。每个工程师（人类或 AI）都知道应该先写测试、应该找到根本原因、应该在声明完成前验证——但在疲惫、时间压力、沉没成本的影响下，这些"应该"很容易变成"这次例外"。

Superpowers 的回答是：**设计一个系统，让"走正确的路"比"走捷径"更容易**。

这个目标通过以下机制实现：
- 铁律消除判断空间
- 门控强制检查点
- 合理化表格预先封堵借口
- 子智能体隔离上下文
- 证据要求防止虚假声明
- 技能测试验证规则有效性

对于希望构建自己工作流系统的人来说，Superpowers 提供的不仅仅是一套具体的技能，更是一套**设计纪律系统的方法论**：找到你最常跳过的步骤，理解你跳过它的借口，然后设计一个让跳过变得更难的系统。
